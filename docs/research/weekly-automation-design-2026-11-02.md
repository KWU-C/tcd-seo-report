# reports_v2 週次レポート自動運用 — 調査・設計（2026-11-02）

対象: `reports_v2` 週次SEO/AIOレポートを、GPT Dot を介さず毎週月曜に自動生成・配信する運用。
今回の範囲は調査・設計・ローカル検証のみ。本番送信・定期実行の有効化・mainへのマージは行っていない。
週次配信の launchd ジョブ（`com.tcd.seo-report.weekly`）は無効のまま、日次AIOジョブ（`com.tcd.seo-report.aio-daily`）は現状維持。

---

## 結論

**B案（月曜9:00開始）を、GSCだけ「確定済みの最新7日間」にする修正版で採用することを推奨する。**

- 処理時間は合計30秒程度（Gmail分類を足しても数分以内）。時間は制約にならない。
- 制約はデータの確定状況。月曜朝の時点で **GSCは金曜分までしか確定していない**（土・日は未確定）。GA4と問い合わせは前週月〜日がそろう。
- そのため、期間を次のように分ける（すべてレポート冒頭に明記する）。

| データ | 対象期間（11/09配信の例） | 比較期間 | 理由 |
|---|---|---|---|
| GA4 アクセス | 前週 月〜日（11/02〜11/08、JST） | 前々週 月〜日 | 月曜朝に日曜分まで取得できる |
| 問い合わせ件数 | 前週 月〜日（Gmail受信日時、JST） | — （4週・12週累計） | メールは即時にそろう |
| GSC 検索順位 | 確定済みの最新7日間（通常 土〜金、10/31〜11/06、米国太平洋時間） | 直前の7日間 | 土・日は月曜朝に未確定 |
| AIO | 月曜朝の観測時点（日時を表示） | 前週の観測 | 時点観測のため期間はない |

A案（金曜17:00締め）は、金曜当日のデータが終わっておらず、GSCは水曜分程度までしか確定しないため、月〜金のどのデータもそろわない。推奨しない。

## 1. 金曜17:00締め（A案）と月曜9:00開始（B案）の比較

| 観点 | A案：金曜17:00締め・月曜配信 | B案：月曜9:00開始・即配信 |
|---|---|---|
| GA4 | 金曜は当日のため未完了。月〜金がそろわない | 前週月〜日がそろう（日曜分は処理中の可能性あり、後述） |
| GSC | 金曜17:00 JST＝金曜01:00 PT。確定は2日前後遅れるため水曜分程度まで | 金曜分まで確定（11/02実測）。土・日は未確定 |
| 問い合わせ | 金曜夕方以降の分が漏れる | 前週月〜日がそろう |
| 週末の扱い | 除外（既存の7日集計と比較できなくなる） | 含む（7日同士で比較） |
| 実行回数 | 生成（金）と送信（月）の2回。失敗点が2つ | 1回 |
| 鮮度 | 月曜配信時点で3日前の集計 | 当日の集計 |
| 判定 | 不採用 | **採用（GSCのみ確定済み最新7日）** |

B案の「GSCも月〜日」は、月曜9:00の時点では土・日が未確定のため、確定値として扱えない（指示書2の条件に反する）。月〜日をGSCにも適用したい場合は、配信を水曜朝に遅らせる必要がある（GSCの日曜分の確定待ち）。

## 3. 月曜時点で取得できるGA4・GSCデータの範囲（2026-11-02 09:50 JST 実測）

### GSC（日付は米国太平洋時間）

- `dataState=final`（既定）: **10/30（金）まで**。
- `dataState=all`: 11/01（日）まで返るが、`firstIncompleteDate = 2026-10-31`。11/01は表示779回（平日は約2,200〜2,500回、土曜10/24は1,468回）で、明らかに途中の値。
- 時間別データは 11/01 10:00 PT（＝11/02 03:00 JST）まで。
- → 月曜朝に確定値として使えるのは **金曜まで**。現在の `offset_days: 3`（実行日−3日）も、月曜実行なら金曜締めになる。
- 確定の遅れは日によって変わるため、固定オフセットではなく、APIの `firstIncompleteDate` から確定日を決める方式（`pipeline.yaml` で「v3以降の拡張」としている auto モード）にする。金曜が未確定の週は、木曜締めの7日間に自動でずらし、注記する。

- 前週月〜日（10/26〜11/01）を取得できた。日曜11/01は121ユーザー（土曜10/31は119、前週日曜10/25は121）で、途中の値には見えない。

## 4. 集計期間の統一と、既存の期間重複の解消

### 期間の決め方

- レポートの「週」は前週の月〜日（JST）。フォルダ名・件名は週の月曜日で一意に決まる形にする（例 `2026-11-02_2026-11-08`）。実行日がずれても同じ週は同じフォルダになり、二重生成・二重配信を防げる。
- GSCは別に `gsc_period`（確定済み最新7日）と `gsc_comparison_period` を持ち、冒頭とSEO表の見出しに明記する。
- 前週比はすべて「同じ曜日構成の7日間同士」。

### 既存データの扱い（削除・上書きしない）

- 既存の `reports_v2/`・`data_v2/processed/` の旧期間フォルダ（10/18〜10/24、10/24〜10/30 など）はそのまま残す。
- GSCの新しい期間は通常「土〜金」になり、本日送信した 10/24〜10/30 とそのままつながる（次回のGSC比較期間＝10/24〜10/30）。前週比の継続性は保たれる。
- 問い合わせ: `inquiries.yaml` の 10/18〜10/24（日〜土）は旧方式の記録として残す。新方式（月〜日）とは期間が1日ずれて重複するため、
  - 旧方式の週は「旧集計（参考）」として、新方式の4週・12週累計には入れない。
  - 新方式の週は、Gmailの受信履歴から過去分もさかのぼって集計できる（認可後）。12週分を初回にまとめて取得すれば、12週累計を最初から確定値として出せる。
  - `inquiries.yaml` の構造変更（旧方式の週の区別）は、承認後に実施する。
- 4週・12週累計は、月〜日の週が連続して欠けなくそろった場合のみ確定値として表示する（現行仕様を維持）。

## 5. Gmail問い合わせ自動分類の実現方法と精度上の課題

### 方式

1. **取得**: Gmail API（`gmail.readonly`）で、前週月〜日（JST）に受信した問い合わせ通知を、送信元と件名の条件で検索する。
2. **除外**:
   - 返信: `In-Reply-To`/`References` ヘッダーあり、または件名が `Re:`/`RE:`/`返信:` で始まるもの（10/18〜10/24 は17通中7通が返信）。
   - 重複通知: 同じ Message-ID、またはフォームの送信番号・送信日時・本文ハッシュが同じもの。
3. **区分**: 専用採用フォームは通知の件名・送信元で判別して別集計。
4. **分類**: 本文で「案件相談／売り込み・提携勧誘／その他」を判定する。
   - 推奨: Claude API（構造化出力）で、ラベル・確信度・理由コード（本文の引用なし）を返させる。確信度が低いもの、採用応募・アンケートなどは「その他（要確認）」へ。
   - 代替: キーワード規則のみ。費用・外部送信はないが、営業文が「ご相談」と書かれている場合（10/18〜10/24 は「協業のご相談」4件がすべて営業）を見分けにくい。
5. **保存**: 本文・氏名・会社名・メールアドレスは保存しない。メモリ上で分類し、ローカルのgitignore対象フォルダ（例 `data_private/inquiries/`）に「メッセージIDのハッシュ・受信日時・フォーム種別・ラベル・確信度・理由コード」だけを残す。レポートに出すのは件数のみ。
6. **確認・訂正**:
   - 配信と同時に、担当者（kawauchi@tcd.jp）宛てに「分類確認リスト」を送る（受信日時・ラベル・確信度・Gmailで開くリンク。本文は載せない）。
   - 訂正は `config_v2/inquiry_overrides.yaml`（ハッシュ→正しいラベル）に書いて再生成する。手入力の `inquiries.yaml` に値がある週は、手入力を優先する。
   - レポートでは、確認前の週は「自動分類（未確認）」、訂正済みの週は「確認済み」と表示する。

### 精度上の課題

- 正解データがない。Dot の分類は週の件数だけで、1通ごとのラベルが残っていない（10/18〜10/24 のみ: 10件＝案件0・売り込み8・その他2）。
- フォームの選択項目と本文の実態が一致しない（営業が「協業のご相談」「お見積り」を選ぶ）。
- 境界があいまいなもの: 代理店からの共同提案、媒体掲載の勧誘、採用応募、自治体・団体のアンケート。
- 案件相談は週0〜数件と少なく、1件の誤分類で成果指標が大きく動く。
- **対策**: 本番化前に4週間、Dot（または担当者）の分類と並行して自動分類を走らせ、1通ごとに一致率を記録する。目安は「案件相談の見逃し0件」「全体の一致率90%以上」。満たすまでは、レポートの問い合わせ件数は手入力の確定値を使う。

### 認証・権限

- 必要なスコープは `gmail.readonly`（Googleの「制限付きスコープ」）。本文を読まないと分類できないため、`gmail.metadata` では足りない。
- OAuthクライアント（GCPプロジェクト 675404374879）の同意画面が「内部（Workspace）」なら、審査なしで使える。「外部」でテスト中の場合、リフレッシュトークンが7日で失効し、無人運用ができない。**同意画面の種別を確認する必要がある**（token.pickle は6月から更新できているため、内部または公開済みの可能性が高い）。
- 既存の `token.pickle`（GSC＋送信）とは別のトークンファイルにし、読み取り権限を分離する。
- 問い合わせ通知が届くアカウント（個人宛て・共有アドレス・グループ）と、認可するアカウントを一致させる必要がある。グループ宛ての場合、グループのメンバーのいずれかのメールボックスを読む。
- Claude APIで分類する場合: APIキーと請求先の用意、問い合わせ本文を外部APIに送ることについての社内確認が必要。

## 6. 推奨する実行環境と運用フロー

### 実行環境: ローカルMac の launchd（第一段階）

実績（日次AIOジョブ、9/2〜11/2）:
- 62日中48日実行。起動したときは毎回 9:30〜9:37 に実行され、スリープ中でも復帰後すぐに実行された。
- 実行されなかった14日は、Macの電源が切れていたか起動していなかった日（主に週末。月曜は9/7〜11/2の9回中、10/5と10/12（祝日）の2回）。
- launchd の時刻指定ジョブは、スリープ中に時刻を過ぎた場合は復帰時に1回実行される。電源オフ中に過ぎた場合は実行されない。
- このMacはノートで、閉じて持ち運ぶ時間帯がある（本日 08:06 にクラムシェルスリープ、08:53 に復帰）。

対策:
- 月曜 9:00・10:00・11:00・12:00 に起動し、その週が送信済みなら何もしない（取りこぼしの再試行を兼ねる）。
- 火曜・水曜の朝にも同じ確認を入れ、月曜に起動できなかった週を補う（遅配として件名に注記）。
- `pmset repeat wakeorpoweron M 08:55:00` で月曜朝に復帰させる（管理者権限が必要。電源オフからの起動は電源接続時のみ確実）。

### 二重配信の防止

- 送信済み台帳: 送信成功時に `state/sent/<週>.json`（送信日時・宛先・Gmailメッセージ ID）を作る。台帳がある週は送らない。再送は `--force-resend` を明示したときだけ。
- 同時実行の防止: 実行開始時にロックを取得し、取れなければ終了する（9/7 の事故は手動実行と自動実行の同時起動が原因）。
- 週フォルダを実行日ではなく週の月曜日で決めるため、日をまたいで再実行しても同じ週になる。

### ログ・エラー通知・再実行

- ログは現行どおり `logs/weekly_report_*.log`。
- 失敗時（取得失敗・データ品質fail・送信失敗）は、kawauchi@tcd.jp にエラー通知メール（失敗した工程とログ末尾）を送る。Macの通知センターにも出す。
- 月曜12:00の時点で未送信なら、その旨を通知する。
- 再実行: `scripts/weekly_report.sh --week 2026-11-02`（週を明示）。台帳により、送信済みの週は送らない。

### 運用フロー（毎週）

1. 月曜 9:00 launchd 起動 → ロック取得・送信済み確認
2. 期間の決定（GA4・問い合わせ＝前週月〜日、GSC＝確定済み最新7日）
3. GSC・AIO・GA4 取得 → 検証 → 正規化
4. Gmail問い合わせ取得・分類（並行運用期間中は参考値として保存のみ）
5. 分析 → レポート生成
6. 配信前チェック（判定不可・データ品質・問い合わせ未入力）→ 問題があっても配信は止めず、担当者に通知
7. unei@tcd.jp へ送信 → 台帳記録 → 担当者に分類確認リスト送付

### クラウド実行との比較

| 方式 | 長所 | 短所 |
|---|---|---|
| ローカルlaunchd（推奨・第一段階） | 追加費用なし。認証情報をMacの外に出さない。既存の仕組みそのまま | Macの電源オフ時は動かない |
| Google Cloud Run ジョブ＋Cloud Scheduler | Macの状態に左右されない | 認証情報をSecret Managerへ移す、過去の処理済みデータ（`data_v2/processed`）をCloud Storageへ移す、Python環境のコンテナ化が必要。設定2〜3日 |
| GitHub Actions | 設定が比較的簡単 | Gmail読み取り・送信権限のトークンをGitHubに置くことになる。履歴データの保存先も別途必要 |

まずローカルで4週間運用し、取りこぼしの頻度を見てクラウド移行を判断する。

## 9. 推奨案と理由

**B案（月曜9:00開始・完了次第配信）を、GSCだけ「確定済み最新7日間」にして採用する。実行はローカルlaunchd、問い合わせの自動分類は4週間の並行運用で精度を確認してから切り替える。**

理由:
1. 処理は30秒程度で終わり、月曜午前中の配信に時間の問題はない。
2. GA4と問い合わせは、月曜朝に前週月〜日がそろう。
3. GSCは月曜朝に金曜分までしか確定しないため、確定済みの7日間を使うことで「未確定の値を確定値として扱わない」を守れる。期間は通常 土〜金 になり、本日送信したレポート（10/24〜10/30）とそのままつながる。
4. A案は、金曜当日・GSCの直近数日・金曜夕方以降の問い合わせが欠け、生成と送信の2回実行が必要になる。
5. ローカルlaunchd は日次AIOジョブで2か月間の実績があり、起動していれば9:30〜9:37に確実に動いている。電源オフの週への対策（月〜水の再試行・未送信通知）を加えれば、月曜午前の配信を十分に見込める。

### 次の判断事項（承認が必要なもの）

1. 上記の期間設計（GA4・問い合わせ＝月〜日、GSC＝確定済み最新7日）でよいか。GSCも月〜日にそろえたい場合は、配信を水曜に変える。
2. Gmail読み取り権限の認可と、Claude APIで本文を分類することの可否。
3. `inquiries.yaml` の旧方式の週（10/18〜10/24）を「旧集計（参考）」として区別する構造変更。
4. 実装後、launchd の週次ジョブを有効化する時期（並行運用の開始時期）。

## 付録: 計測方法

- 計測は 2026-11-02 09:50〜10:00 JST、`/usr/bin/python3`（3.9.6）。
- GSC・GA4の取得は、既存の `fetch_gsc.fetch_period` と `fetch_ga4.fetch_segments` を、出力先を作業用の一時フォルダにして実行した（`data_v2/` は変更していない）。
- GSCの確定範囲は `searchanalytics.query` の `dataState=final/all/hourly_all` と、応答の `metadata.firstIncompleteDate` で確認した。
- 分析・生成は、本日の `normalized.json` を一時フォルダにコピーして実行した。
- AIOは追加のSerpAPI検索を行わず、本日の本番実行のraw保存時刻から求めた。
- 日次AIOジョブの実行実績は `logs/aio_daily_YYYYMMDD_HHMMSS.log` のファイル名から集計した。
