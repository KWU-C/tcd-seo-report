## 0. 結論（要約）

1. **Looker Studio のページ別の数値（1,855、1,362 など）は、実際のユーザー数ではない。** 表の指標が「28日間のアクティブユーザー数」（GA4 の `active28DayUsers`）で、これを日ごとに28日分足した値になっている。実データの問題ではなく、Looker Studio の表の指標設定の問題。実際の28日間のユーザー数は、企業ブランディング支援が67人、日東電工の事例が53人。
2. **サイト全体の −29.5% は、検索順位の低下によるものではない。** 減少分 384人のうち、直接流入の減少が346人。中身は「前週 10/15 の一時的な集中アクセス（メール配信の可能性）」と「中国（新疆）からのボットに近いアクセスの減少」。国内の自然検索のセッションは 452 → 449 で横ばい。Search Console のクリック数は 253 で、直近10週で最も多い。
3. **東京は順位7〜10位を維持しているが、クリックがほぼない。** 「東京 ブランディング会社」は28日間で173表示・2クリック（/tokyo）。検索結果の上部に地図枠（3社）、AIO、比較記事が並び、TCDは地図枠に出ていない。
4. **インナーブランディングの「約29位」は、主力ページの実力より低く見えている。** 週次の値はクエリ単位の平均順位で、69〜98位に出る旧ページ（/service/about_innerbranding.html）の表示が平均を押し下げている。主力ページ（/branding/definition/inner-branding.html）だけで見ると 25.0位 → 19.7位と、8週で改善している。ただし上位10ページが共通して扱う「目的・メリット・施策・事例」の見出しがなく、10/02 に作った改稿案は未反映。
5. **東京AIOでは、TCDのURL引用と推薦企業としての紹介を、どちらも確認できた（10/27取得分）。** ただし日次（10/14〜10/27）で推薦を確認できたのは2日だけで、7日は判定できなかった。安定して推薦されているとはいえない。
6. **10/18〜10/24 の営業成果: 問い合わせ10件、うち案件相談0件・売り込み8件・その他2件**（専用採用フォームの1件は別集計）。GA4 の「問い合わせ完了6人」とは数えている対象が違い、計測不具合とは断定しない（2-4）。SEO/AIO施策の成果は、問い合わせの総数ではなく **案件相談件数** で判断する（6章・8章）。

## 1. GA4・Looker Studio の数値整合性

### 1-1. 数値の照合（GA4 Data API で再集計）

Looker Studio の「過去28日間」は **2026-09-29〜10-26**（今日を含まない28日）。

| Looker Studio の表示 | Looker の値 | GA4 activeUsers（同期間） | GA4 active28DayUsers の日別合計 | 判定 |
|---|---:|---:|---:|---|
| サービス系 全体（スコアカード） | 264 | **264** | — | 一致（正しい） |
| Works 全体（スコアカード） | 854 | **854** | — | 一致（正しい） |

- スコアカードは `activeUsers`（期間中のユニークユーザー）、表は `active28DayUsers`（「その日までの28日間」のユーザー数）を使っている。後者を28日分の日付で集計すると、同じ人が最大28回数えられる。そのため、ページ別の値がセグメント全体を上回る。
- マガジン系（/branding/）とワークス系の表も同じ指標で、同じ問題がある。例として、/branding/kawauchi/inner_05.html の「+11,761%」は、10/15 の集中アクセスが28日間の移動合計に残っているため。
- 週次レポートの GA4 の値は `activeUsers` を使っており（`src_v2/fetch_ga4.py`）、こちらは正しい。コード内のコメントにも「active28DayUsers はページと組み合わせると重複集計になるため使わない」と書かれている。
- ページ別 activeUsers が 67 と 76 の2通りになっているのは、GA4 のユーザー数がフィルタやディメンションの指定方法によって近似値で変わる仕様のため（HyperLogLog による推定）。どちらも1,855とは桁が違う。

**切り分け: 実データの問題ではなく、Looker Studio の表の指標設定の問題。**

### 2-4. 別に注意が必要な点

- **問い合わせ完了（/contact_end）の到達は6人で、直近10週で最も少ない**（前週20、前々週26、10週の平均は約15）。

- 入力: Dot または担当者が、確認済みの週次集計値（件数のみ）を `config_v2/inquiries.yaml` に手入力する。レポートの生成時に読み込む。

- サーバー側で届いていない分は把握できない。レポートには「メール通知から確認した件数」と注記する。
- 配信の手順は「件数の記入 → pipeline → analysis → build → send」となり、記入が配信前の確認項目になる。
- Gmail 連携・スプレッドシート連携は実装しない（2026-10-27 の決定）。

### 8-4. 実装する場合の作業（参考）

- `config_v2/inquiries.yaml` の新設（週の開始日をキーに、5項目の件数と「要確認」件数、確認方法の注記）
- `src_v2/report/view_model.py` と HTML/Markdown の描画に表を追加。未入力の週は「未入力」と表示する
- `tests_v2` にテストを追加（未入力、0件、案件相談ありの3通り）
- 工数の目安: 2〜3時間。実装・配信形式の変更はユーザーの承認後に行う
